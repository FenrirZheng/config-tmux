#+TITLE: ADR-0006: Port sift from C++/cmake to Rust, keep libc regex FFI
#+STATUS: accepted
#+DATE: 2026-08-31
#+DECIDERS: @fenrir

* Context and Problem Statement

[[file:0005-own-the-interaction-loop-for-regex-search.org][ADR-0005]] (2026-08-27) decided that ~prefix /~ needed its own interaction loop
— a popup program that lists every regex match live, then hands the actual
jump back to tmux. That decision was implemented as C++, built by cmake,
deliberately outside the =tools/= cargo workspace — a divergence
=tools/ARCHITECTURE.org= recorded as "a user directive, not a technical
finding". The cost was real and was paid every time the toolset was built or
cloned fresh: a fresh-machine bootstrap needed a C++20 compiler and cmake in
addition to cargo, the fresh-clone instructions grew a second build command,
and because cmake wrote =sift='s binary into the same =tools/target/release/=
directory the cargo binaries use (so =claude.conf= could keep one path shape
for every tool), =cargo clean= silently deleted =sift= along with the Rust
binaries — a footgun the runbook had to carry a standing warning about.

On 2026-08-31 =sift= was rewritten in Rust as a full member of the =tools/=
cargo workspace. This ADR records that decision, and — because the two choices
are entangled — the regex-engine choice made alongside it: whether the ported
program keeps calling glibc's =regcomp=/=regexec= through FFI, or switches to
the idiomatic Rust =regex= crate now that the language allows it.

* Decision Drivers

- *Single build system.* Every other binary in =tools/= is a cargo workspace
  member; =sift= being the lone exception meant two build commands on every
  fresh clone, and forgetting the second left =prefix /= bound to a "not built"
  stub — the exact failure mode the stub message existed to explain.
- *The =cargo clean= footgun.* Sharing =target/release/= between cmake and
  cargo output was what kept the binary paths uniform, but it meant a routine
  =cargo clean= took =sift= down with the Rust tools without saying so.
- *Regex-dialect fidelity.* =sift= only builds the candidate list; tmux
  performs the actual jump-and-highlight via its own =search-backward=/~n~/~N~
  (ADR-0005's chain-preserving design). If sift's matcher and tmux's disagree
  about what a pattern matches, the two can point at different occurrences
  after a jump — silently, since nothing checks candidate-list agreement at
  runtime.
- Single maintainer, the same driver ADR-0005 named: fewer languages and build
  systems to carry indefinitely.

* Considered Options

- Option 1: Rust, matching tmux's regex dialect via =libc= FFI
  (=regcomp=/=regexec= with =REG_EXTENDED=, plus =wcwidth=, =termios=, =poll=)
- Option 2: Rust, using the =regex= crate
- Option 3: Leave =sift= as C++/cmake

* Decision Outcome

Chosen option: "*Option 1*", implemented as [[file:../tools/sift/src/main.rs][=sift/src/main.rs=]].

tmux's own search runs POSIX extended regex through glibc =regcomp(REG_EXTENDED)=:
leftmost-*longest* matching, backreferences, =\<=/=\>= word boundaries, and =\d=
read as a literal =d=. The =regex= crate is, by its own documentation, not
POSIX-compliant on any of those points — it uses leftmost-first (Perl-style)
matching, has no backreferences, and treats =\d= as a digit class. Swapping
engines would desynchronise sift's candidate list from what tmux's =n=/=N=
chain actually finds, which is precisely the risk ADR-0005's "Neutral"
consequence flagged: *"if [the two engines] ever diverge, the list would offer
hits the jump cannot reproduce."* Reaching for glibc's own =regcomp=/=regexec=
through FFI is not a stopgap short of a "proper" Rust regex library — it is the
only choice that keeps the guarantee, because it calls the identical engine
tmux itself uses. =wcwidth= is FFI for the matching reason: it must agree with
the same locale-aware width table tmux's own display and =#{copy_cursor_x}=
implicitly assume, and the =unicode-width= crate does not read glibc's locale
tables.

Rust was chosen over "leave it C++" because workspace membership removes the
second build system entirely — no cmake, no C++20 compiler requirement, and no
shared-output-directory footgun with =cargo clean=. The port was verified,
not merely typed and shipped: =verify-sift-jump.sh= (13 assertions) and
=verify-sift-live.sh= (6 assertions) both pass at the same counts as the C++
baseline, =sift rows= output was checked byte-identical across 26 regex
patterns, 26 differential rendering comparisons between the two binaries
matched, and three adversarial audits of the port turned up zero blocking
findings.

This ADR narrows nothing in ADR-0005. The interaction loop's shape — =sift=
owns keystrokes and the candidate list, tmux owns the actual search and the
jump — is exactly as that ADR left it. This is a language and build-system
decision layered on an unchanged architecture.

** Consequences

- Good, because the toolset is a single =cargo build --release= again — the
  fresh-machine bootstrap loses a step, and =cargo clean= no longer needs a
  special warning about =sift=.
- Good, because the regex engine keeps exact dialect fidelity with tmux's own
  search, which is the property ADR-0005's chain (highlighting, =n=/=N=, and
  seek's grab keys) depends on after a jump.
- Good, because the port's differential testing surfaced and fixed two
  long-standing C++ bugs: =Home=/=End= used to leak a literal =~= into the
  pattern instead of jumping to the first/last match (the numeric CSI forms
  tmux actually sends, =ESC[1~=/=ESC[4~=, were never recognised); and
  resizing the popup used to cancel the search outright (=SIGWINCH= was
  reported as =Esc=) instead of redrawing at the new size.
- Bad, because =libc= is now a real dependency the crate reaches through
  =unsafe= FFI calls (already a workspace dependency for =seek='s own
  =wcwidth= use, so this adds no new crate to the tree, but =sift= is the
  first crate here whose *core* logic — the regex matching, not just one
  helper — lives behind FFI). The safety argument is carried in per-call-site
  =SAFETY= comments rather than by the type system, which a pure-Rust crate
  would not need to write.
- Neutral, because =sift= still has no =tmuxlib=: exactly as under C++, it
  re-implements the =tmux= subprocess call and the literal-message helper
  itself (=tools/ARCHITECTURE.org=, "Crates").

* Pros and Cons of the Options

** Option 1: Rust + libc FFI (regcomp/regexec, wcwidth, termios, poll)
- Good, because the match set stays provably identical to tmux's own search —
  same libc, same =regcomp= call, same locale-aware =wcwidth=.
- Good, because it is a normal cargo workspace member: one build system.
- Bad, because the FFI calls are =unsafe= and each needs a written safety
  justification at the call site.

** Option 2: Rust + the =regex= crate
- Good, because it needs no =unsafe= and no FFI at all.
- Good, because it is the idiomatic choice for a Rust program with no other
  constraint, and the crate most Rust developers would reach for first.
- Bad, because it is not POSIX ERE: leftmost-first instead of
  leftmost-longest, no backreferences, =\d= means a digit class instead of a
  literal =d=. Any of those differences can make sift's candidate list
  disagree with what tmux's =search-backward=/=n=/=N= actually find, silently
  breaking the post-jump chain ADR-0005 built the whole feature around.

** Option 3: Leave sift as C++/cmake
- Good, because it is zero-risk — no port to verify, no regression surface.
- Bad, because the second build system — and its =cargo clean= footgun — stays
  permanently, which is exactly the cost ADR-0005 accepted as a bounded,
  one-tool exception, not a fixture to keep indefinitely.
