- Row layout is now ="> "= (2) + ordinal (=ordw=) + space + line number (=numw=) + space

*Three decisions taken beyond ADR-0007's literal text* — recorded explicitly, since a
future reader cannot derive them from the ADR:

1. *The invariant extended to every mover.* ADR-0007 names only the arrow keys as
   rewriting the buffer, but its stated invariant — "=goto>= always names where the
   cursor actually is" — does not hold unless every mover does, so =sync_ordinal()= is
   called from =Up=, =Down=, =Home=, =End= and the =PgUp=/=PgDn= block.
2. *=C-w= / =C-u= clear the buffer before touching the pattern.* The ADR does not name
   them. Chosen over ignoring them so the load-bearing property "no exit from the mode
   happens after the pattern changes" stays true — both call =refilter()=.
3. *=Alt-<digit>= pressed while already in the mode extends the buffer*, exactly like
   a bare digit, rather than restarting it.

*A blocking regression was found by an independent verifier and fixed* — the most
useful finding in this ticket:

The new footer (=↑↓ select  left-Alt-digit goto  Enter jump  Esc cancel  C-w word  C-u
clear=) is 75 display cells, up from 54, and =draw()= emitted it with *no width guard
at all*. =draw()= is contracted to emit exactly =h= lines — header + =h-2= rows +
footer — so at any sift width <= 74 the footer wrapped, the pane scrolled, and the
*header went off the top of the screen*, taking the =goto>= prompt and the match count
with it. The user would be in a mode with no on-screen evidence of it.
=claude.conf:207= sizes the popup at =-w 95%=, so any tmux client narrower than ~81
columns was affected; the user's own 282-column client was not. It contradicted
ADR-0007's settled "the mode is never invisible", so it blocked.

Fixed by a new =utf8_fit(std::string_view, int budget)= — the forward inverse of the
existing =utf8_cells=, built from the same decoder, cutting on a character boundary;
=kDim=/=kReset= are zero-width and are neither charged against the budget nor cut. The
footer /text/ is unchanged, so ADR-0007's "left Alt" wording and every doc quoting the
footer still match the binary.

Verified by a width sweep at w = 20, 30, 40, 60, 74, 75, 100, 265 — *8/8 pass*; and the
sweep was shown to have teeth by running it against an unguarded control binary
differing only in the reverted guard line: *5/8 FAIL*, at exactly the predicted w=75
boundary. Worth saying plainly: the verifier's behavioural lens passed *25/25 at 100
columns* while the feature was invisible at 74. Only a lens aimed at "can the user
actually see the number" caught it.

The independent verifier walked all 25 of ADR-0007's settled decisions with pasted
evidence from the running binary: 23 implemented, 1 out-of-scope (the ordinal column
width question — see Not yet specified), 1 blocking (the footer, now fixed), plus the
docs gap that [[#t4][t4]] then closed.

*** Resolution

*The change is one string literal* in =tools/sift/src/main.cpp=:

: ↑↓ select  left-Alt-<n> goto match n  Enter jump  Esc cancel  C-w word  C-u clear

*Why =match n= and not =#n=.* =#n= was the first candidate and was rejected on two
grounds, the first local and decisive: in this repo =#= is tmux format syntax
(=#{pane_id}=, =#{copy_cursor_x}=), so a =#= that is *not* a format is a collision at
exactly the place a reader is trying to parse. Second, the rows render bare numbers,
never =#=-prefixed, so =#n= would have asked the reader to invent the mapping =#= ->
the cyan column. =match= is the one candidate word with a referent chain already on
screen: the header's =N matches=, the ordinal column itself, and the glossary term
[[file:../../CONTEXT.org][Match ordinal]]. Lowercase =n= is deliberate — capital /N/
is the *total*, so =goto match N= would have named the last candidate.

The angle brackets stay: =left-Alt-n= reads as Alt plus the letter =n=, a real key
nobody should press.

*The footer went 75 -> 81 cells, and that is an advantage, not a cost.* A shorter form
(=left-Alt-n goto #n=, 74) was available and was rejected: [[#t3][t3]]'s narrow-width
assertion runs at 74x20 precisely /because/ 74 is below the footer width, so
=utf8_fit= must act. A 74-cell footer would fit exactly there, and that assertion
would then pass on a guarded *and* an unguarded binary — keeping its wording while
losing its teeth. The same species of defect as the two [[#t3][t3]] caught.

*The suites gain two assertions* (live 17/0 -> *19/0*; jump unchanged 13/0), both in
§8, which is now "the header survives a narrow pane, and the footer fits its own
budget". The obvious assertion was rejected as near-vacuous: =utf8_fit= cuts from the
*right* and the new item sits at cells 12-36, so "the item survives the cut" is true
at any width >= 36 and could never redden — every future addition lands after it.
What growth actually threatens is the tail. So the assertion is *the whole footer
line, at exactly its own width* (81x20, geometry fail-closed), where one added cell
