# Draft Resolution for t2 (researcher output, pre-review)

**Shortlist: tuned tokyo-night, catppuccin/tmux, dracula/tmux.**

Tuned tokyo-night stays in as the low-risk incumbent — it already satisfies every collision axis from t1 (last-line load order, cc-beacon's three-key cache, no `pane-border-status` fight once `claude.conf` is last) because that's the config running today; the only changes are turning `transparent` off and adding hex overrides for the 6 raw-default interactive elements. **`transparent 0` is not a no-op.** Per the kb atom the option is inert only for the *statically*-set options — `status-style` was already baked opaque `#1A1B26` at TPM load despite `transparent 1` — while the per-invocation widget scripts re-source `themes.sh` on every refresh and therefore honor it live: the git and path cells emit `bg=default` and show Alacritty's translucent background *today*. Setting it to 0 makes those cells opaque, and the proposed `window-style`/`window-active-style` overrides go much further (see gaps).

catppuccin/tmux (flavor `mocha`) is the strongest maintained alternative: it covers 5 of the 10 interactive-element options out of the box (vs tokyo-night's 4), including `popup-style`/`popup-border-style` which tokyo-night never touches, ships a first-class transparent mode, writes zero `pane-border-status`, and had a tagged release 4.5 months ago. Caveat on that 5: one of them, `mode-style`, is written **bg-only** (`catppuccin_tmux.conf:224`, `bg=#{@thm_surface_0},bold` — no `fg`), so copy-mode selection foreground falls through to the terminal default; that is a *downgrade* from tokyo-night's fg+bg `mode-style`, and it is the same asymmetry that counts against rose-pine below. Call it 4 full + 1 partial. It is also the **contrast leader of the survey**: 12.14:1 status text (`@thm_fg` `#cdd6f4` on `@thm_mantle` `#181825`).

dracula/tmux earns its shortlist slot on **module parity plus maintenance, not on contrast**. It is the only surveyed alternative that ships *both* halves of tokyo-night's widget parity natively: a git module (`scripts/git.sh` — branch + A/M/U/D change counts, pure bash+git, no external binary — where catppuccin's git module shells out to `gitmux`, which is not installed here) and a `~`-abbreviated full-path cwd module (`scripts/cwd.sh`, with truncation options — where catppuccin and rose-pine offer basename only). It was last touched 2 days ago (2026-08-22), by far the most active repo surveyed. Its status-bar text contrast under this draft's own try-on options is 8.59:1 (white `#f8f8f2` on gray `#44475a`) — strong and comfortably above AA, but **not** the survey's best; catppuccin's 12.14:1 is. And it sets exactly **1** of the 10 interactive-element options (`message-style`, `dracula.sh:174` — the same white-on-gray pair, so also 8.59:1), leaving 9 overrides as new work.

**Does the 3-candidate shortlist survive that correction?** Yes, but for a different reason than first written. Dracula was originally shortlisted for "best raw contrast"; that claim was wrong (13.36:1 is the white-on-`#282a36` powerline-separator pairing, which the `@dracula-show-powerline false` try-on below never renders as status-bar background). What remains is still unique in the pool and still load-bearing against t1's axis checklist: dracula is the **only** candidate that clears the git-module *and* path-module parity bars with zero external dependencies and zero custom `status-right` composition, and it is the most actively maintained. Catppuccin needs an absent binary for git parity and a custom `@catppuccin_directory_text` for path parity; every cut candidate fails one or both outright. So the composition (tuned tokyo-night, catppuccin, dracula) stands — with the honest trade restated as "native parity + freshest upstream, at the cost of 9 hand-written interactive-element overrides and second-place base contrast."

Cut from the pool:
- **rose-pine/tmux** — cut primarily on **contrast**: its own default status-bar text contrast is 3.38:1 — below WCAG AA for normal text, i.e. it fails the entire point of this effort by its own defaults (`rose-pine-tmux/rose-pine.tmux:113`, `thm_pine` `#31748f` fg on `thm_base` `#191724` bg). Note that this is *not* the weakest coverage surveyed — dracula's 1/10 is — but egel has none of dracula's compensating strengths (no native modules, stale upstream), so coverage was never the deciding axis for it.

**Shared try-on/rollback procedure (all three)**

**`source-file` never unsets anything.** Every option the *outgoing* theme wrote survives into the incoming one unless the incoming theme happens to write the same option. Tokyo-night → catppuccin is the worst case in this pool: catppuccin writes no `status-left`/`status-right`/lengths, no `pane-border-*` and no `window-status-separator` — so tokyo-night's `status-left-length 80`, `status-right-length 150`, its `status-left`, its pane-border colors and `window-status-separator ""` would all silently persist and be judged as if they were catppuccin's. Reset explicitly.

1. Edit `tmux.conf` for the candidate (comment out the previous theme's plugin+option lines; the last line, `run-shell 'tmux source-file ~/.tmux/claude.conf'`, must stay literally last).
2. If the plugin changed: `prefix I` to install.
3. **Unset the outgoing theme's writes**, so the incoming theme is judged on its own defaults. Tokyo-night's full written set is `tokyo-night.tmux:15,16,20,22,23,25,26,27,29,30,71,75,77,80,81` — the same 15 options t1's current-value table lists, seen from the writer's side — and the tuned block above adds 6 more:
   ```
   tmux set -gu status-left-length; tmux set -gu status-right-length
   tmux set -gu status-left;        tmux set -gu status-right
   tmux set -gu status-style
   tmux set -gu mode-style;         tmux set -gu message-style
   tmux set -gu message-command-style
   tmux set -gu popup-style;        tmux set -gu popup-border-style
   tmux set -gu pane-border-style;  tmux set -gu pane-active-border-style
   tmux set -gu pane-border-status
   tmux set -gu window-status-format
   tmux set -gu window-status-current-format
   tmux set -gu window-status-separator
   tmux set -gu window-style;       tmux set -gu window-active-style
   tmux set -gu copy-mode-match-style
   tmux set -gu copy-mode-current-match-style
   tmux set -gu copy-mode-mark-style
   ```
   Switching *away* from catppuccin or dracula: same list, plus that theme's extras — catppuccin also writes `menu-selected-style` (`catppuccin_tmux.conf:44`) and `clock-mode-colour` (`:225`); dracula also writes `clock-mode-style` (`dracula.sh:156,158`), `window-status-activity-style` and `window-status-bell-style` (`:405,:406`). ## Uncertainties

- The copy-mode-*-style hex overrides proposed for tuned tokyo-night are **[判斷]** — untested against the live server, not yet visually confirmed; only the arithmetic WCAG-ish ratio is computed.
- Neither rose-pine's nor catppuccin's `mode-style` contrast could be computed: both set `bg` only (`rose-pine.tmux:478` `bg=${thm_hl_med}`; `catppuccin_tmux.conf:224` `bg=#{@thm_surface_0},bold`), so the effective `fg` is whatever Alacritty's default foreground resolves to — out of scope to verify here. This is recorded as a **shared caveat on both**, not as a discriminator: rose-pine's cut rests on its 3.38:1 default status text, and catppuccin's coverage is scored 4 full + 1 partial because of it. Neither is a hard number.
- t1's copy-mode-*-style table entries use tmux's *named* colors (`cyan`/`magenta`/`red` on `black`), not hex; their real rendered contrast depends on Alacritty's ANSI palette (out of scope per the map), so the "raw default" baseline itself is not fully hex-verifiable — this is exactly why hex overrides (as proposed for tuned tokyo-night) are preferable to leaving named-color defaults in place, but it also means the *current* 4/10-vs-10/10 framing undercounts how "bad" the true-color defaults are until seen live.
- All WCAG-style contrast numbers in this draft use a standard sRGB relative-luminance formula, not a rendered-terminal measurement — treat them as decision-support arithmetic, not a substitute for t3's live-in-terminal judgment call.
- catppuccin's `@catppuccin_status_gitmux`/`@catppuccin_status_directory`/`@catppuccin_status_session` module-variable names used in the try-on block are read from `utils/status_module.conf:30` (`"@catppuccin_status_${MODULE_NAME}"`) — pattern-verified but not live-tested end-to-end on this machine.

## reusable_findings

**TPM's plugin directory name is the repo basename, not a namespaced tag — same-named theme repos collide.** `plugin_functions.sh:86-88` (`plugin_name_helper`) takes `basename(user/repo)`. `catppuccin/tmux`, `dracula/tmux`, and `rose-pine/tmux` are all literally named `tmux`, so all three clone to the identical path `~/.tmux/plugins/tmux/`. Any future TPM-plugin comparison workflow in this repo must `rm -rf` (or rename) the shared directory between candidates, not just edit the `@plugin` line — editing the line alone leaves stale files from the previous candidate in place for TPM to silently reuse.

**TPM only sources a plugin's top-level `*.tmux` files — nested entry scripts are invisible to it.** `source_plugins.sh:17` globs `$plugin_path*.tmux` with no recursion. A repo that ships its tmux integration nested (nightfox.nvim's `extra/<variant>/<variant>.tmux`) is not a working TPM tmux-theme plugin regardless of what its README implies about being installable — verify with a literal top-level `ls <clone>/*.tmux` before ever proposing `set -g @plugin` for a theme repo.

**`tmux source-file` is additive — swapping themes by editing the `@plugin` line leaves the outgoing theme's writes in place.** tmux options have no "reset to what the config says" semantics: re-sourcing `tmux.conf` only *re-executes* `set` commands, so any option the outgoing theme wrote and the incoming one does not write silently persists and gets attributed to the incoming theme. A theme A/B comparison is therefore only valid if it is preceded by an explicit `set -gu` of the outgoing theme's full written set (derive it by grepping the theme's entry script for `tmux set`), or run on a fresh `tmux -L <socket>` server. Verified 2026-08-24 on 3.5a: all 21 option names in the shared procedure above `set -gu` cleanly back to compiled-in defaults.

**tmux's style-option parser accepts space or comma between attributes — don't flag space-separated `set-option` style strings as bugs.** Empirically verified on the installed tmux 3.5a (`tmux -L <isolated-socket> set-option -g mode-style "fg=X bg=Y bold"` succeeds and round-trips via `show-options`), contrary to the assumption that only comma-separated attribute lists are valid. Relevant because at least one surveyed theme fork (z3z1ma/tmux-gruvbox) builds space-joined style strings that looked suspicious at a glance.
