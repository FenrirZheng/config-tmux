- [[#t3][seek CLI surface and failure contract]] — seek is a subcommand CLI (word/line/back) that computes the text itself and shells to wl-copy; to-claude speaks for the Claude keys; a load-time if-shell guards the missing binary
- [[#t4][Key-table coverage and documentation surface]] — pin mode-keys and status-keys instead of double-binding; seek gets a runbook, per-key cheat.txt entries, one row in each ARCHITECTURE table, and a tools/ workspace step in the parent bootstrap
- [[#t5][Origin stamp contract redesign]] — stamp deleted: search_present is the liveness signal, backward search already lands on the match start, v is removed, and delivery exits copy-mode
- [[#t6][Clipboard delivery ownership across the output keys]] — all four keys write wl-copy plus set-buffer, seek owns both sinks uniformly, wl-copy failure degrades with a changed message, and to-claude's exit code is swallowed
- [[#t7][Status-line message safety and shape]] — all seek messages use display-message -l (injection structurally impossible), text truncates at 48 via tmuxlib, and the alt-screen suffix rides only on live-search deliveries
- [[#t8][Binding placement and load ordering]] — seek block lives in claude.conf (loads last), the two pins go in tmux.conf's options area, sensible turns out to re-pin status-keys to the same value, and the prompt label is one conditional binding with a specified two-branch fallback
- [[#t9][Undefined input semantics]] — seek extracts the whitespace-delimited token itself (copy_cursor_word fragments paths), trims surrounding punctuation and the query, and the path rule is slash or line-number or letter-bearing extension
- [[#t10][Rollback and cutover for the thumbs removal]] — delete the thumbs tree at cutover as originally decided, make the cutover one atomic commit so rollback is one git revert, and record the auto-rebuilding restore recipe in the runbook

*** Question

Does `tmux set-buffer` alone reach the Wayland system clipboard under
`set-clipboard on` (via OSC 52) in this alacritty + tmux 3.5a setup, or must
`seek` shell out to `wl-copy` the way every existing capture-rail path does?

The comment at tmux.conf lines 63-66 records an observation that it does NOT:
tmux-thumbs' stock uppercase command used `set-buffer` + `paste-buffer` and left
Ctrl+Shift+V pasting whatever was in the system clipboard from before, which is
why `@thumbs-command` and `@thumbs-upcase-command` were both rewritten to pipe
through `wl-copy` explicitly. That observation predates the current terminal and
tmux versions and was never re-tested.

This decides whether seek's clipboard path is one tmux call or a shell-out, so it
blocks the CLI surface. Answer with a measurement, not a reading of the docs:
set a buffer from a detached command, then read the actual Wayland selection back
with `wl-paste`, with a real client attached and again with none.

*** Resolution

Measured on tmux 3.5a + alacritty 0.15.1, this machine, 2026-08-09.

| operation                                     | tmux buffer | Wayland clipboard |
|-----------------------------------------------+-------------+-------------------|
| =set-buffer=                                  | set         | unchanged         |
| =copy-pipe-and-cancel=, background window     | set         | unchanged         |
| =copy-pipe-and-cancel=, visible pane          | set         | set               |
| OSC 52 written straight at the client tty     | n/a         | set               |

Answer: =set-buffer= alone does NOT reach the Wayland clipboard, so the observation
recorded at tmux.conf lines 63-66 is still accurate today — and the mechanism behind
it is now known. tmux emits the OSC 52 escape only on *copy* events; setting a buffer
is not one. A scripted-client capture showed no =ESC]52;= whatsoever for =set-buffer=,
while =select-word= followed by =copy-pipe-and-cancel= emitted =ESC]52;;YWxwaGE=,
which is base64 for "alpha" — the word that was selected.

alacritty is not the limiting factor: =osc52 = "CopyPaste"= at alacritty.toml line 69,
and writing an OSC 52 sequence straight at the client tty set the clipboard
immediately. Neither is terminfo: the =Ms= capability is present for alacritty,
xterm-256color and tmux-256color alike, so the negative results above are real
negatives rather than capability artifacts.

One further condition, also measured: the copy path reached the clipboard only when
the pane was visible in the client's current window. The identical copy performed in
a detached background window set the tmux buffer and left the clipboard untouched.
seek's output keys are always pressed in a pane the user is looking at, so the
condition holds in real use — but it rules the copy path out for anything headless.

Consequence for the spec: seek cannot use =set-buffer= for the clipboard half. Two
routes survive, and choosing between them belongs to the CLI surface ticket.

- Shell out to =wl-copy=, as every existing capture-rail path does. Works regardless
  of pane visibility and with no client attached.
- Drive =select-word= or =select-line=, then =copy-pipe-and-cancel=, and let
  =set-clipboard on= deliver. The clipboard comes free, the selection highlight comes
  free, and =copy-pipe= can pipe to a command in the same call — which is exactly how
  =copy-mode Y= already reaches to-claude. Two caveats: it needs the visible-pane
  condition above, and =copy-pipe-and-cancel= exits copy-mode, which conflicts with
  the =v= key's decision to stay there.

Probe scripts: [[file:assets/scripts/osc52-probe.sh][osc52-probe.sh]] and [[file:assets/scripts/osc52-probe2.sh][osc52-probe2.sh]].

*** Question

Five observable behaviours the spec must state, all graduated from the design
interview's open items. Each is a decision, not a discovery:

1. Empty query followed by Enter — undefined today. Does `seek` treat it as a
   cancel, or leave the cursor where copy-mode entry put it?
2. A query matching only deep in the scrollback jumps the view far from the
   current screen (history-limit is 100000). Bound the search range, or accept it?
3. A match spanning two words (querying `a b`) leaves `copy_cursor_word` returning
   only the word under the cursor, not the whole match — measured. What does the
   `w` / `W` word grain mean in that case?
4. copy-mode in an alt-screen pane (vim, less, claude fullscreen) has only the
   visible region, no scrollback. Should `seek` warn there the way `to-emacs` does
   (commit 33b86e5), stay silent, or refuse?
5. `prefix Space` runs `set-mark` so a cancel can be undone with `M-x`, which
   clobbers a manually set mark. Acceptable, or should the origin be tracked some
   other way?

Answering these fixes what the binary observes and reports, so it blocks the CLI
surface ticket.

*** Resolution

Settled in [[file:grill/2026-08-09-1218-search-prompt-edge-cases.org][the 2026-08-09-1218 grill snapshot]], which carries all ten decisions with
their measurements, the nine rejected alternatives, and the four open items. The
five questions this ticket asked, answered:

1. Empty query plus Enter keeps tmux's native behaviour — the cursor returns to the
   copy-mode entry origin and the pane stays in copy-mode.
2. A deep-scrollback match is allowed to jump the view. This was not a preference:
   tmux has no range-limited search command, so bounding would mean writing our own
   search engine, the architecture ADR-0001 rejected.
3. Word grain is hybrid — a single-token query yields the containing word, a query
   containing whitespace yields the matched text. Measured: =select-word= and
   =copy_cursor_word= both return only =alpha= for a match on =alpha bravo=.
4. Alt-screen panes are warned about twice: the prompt label branches through
   =if-shell -F '#{alternate_on}'=, and seek appends to-emacs's wording to its
   =display-message=. An entry-time =display-message= alone was measured to be
   overwritten by the prompt.
5. =set-mark= clobbering a manual mark is accepted; =M-x= stays the way back.

Three decisions the grill added beyond the five asked:

- The prompt opens empty rather than prefilled the way stock =C-r= is.
- Liveness is detected by a one-shot =@seek_origin= stamp, consumed with =set -p -u=
  before seek acts, because =pane_search_string= is sticky — it still read =axb= after
  a later empty search, so trusting it would grab text the user never selected.
- With no stamp present the five keys act as general copy-mode grabbers, skipping the
  =cursor-left=; =v= alone fails closed there.

One measurement removed work rather than adding it: =search-backward-incremental= is
plain text, not a regular expression — verified with a positive control — so the
plain-substring decision needs no enforcement code.

Carried forward: the hybrid grain constrains the copy-pipe route still open in the CLI
surface ticket, since =select-word= cannot express the multi-token case.

*** Resolution

Settled in [[file:grill/2026-08-09-1304-cli-surface-and-failure-contract.org][the 2026-08-09-1304 grill snapshot]], which carries all seven decisions with

The contract, per key:

| key | invocation           | reads                                         | reports          |
|-----+----------------------+-----------------------------------------------+------------------|
| =v= | =seek back=          | @seek_origin, pane_search_string              | nothing          |
| =w= | =seek word=          | + copy_cursor_word or the query, alternate_on | =→ CLIP <text>=  |
| =W= | =seek word --claude= | same                                          | to-claude speaks |
| =l= | =seek line=          | + copy_cursor_line, alternate_on              | =→ CLIP <text>=  |
| =L= | =seek line --claude= | same                                          | to-claude speaks |

Every binding passes =#{pane_id}= explicitly — measured: a copy-mode binding expands its
formats against the pane the key was pressed in rather than the active pane, so with
=%41= in copy-mode and =%42= active the binding read =pane_id=%41 x=6 y=0 word=[bravo]=,
matching =%41= exactly.

The ARCHITECTURE.md conventions, restated concretely: every path exits 0, including all
three fail-closed cases, because a non-zero exit becomes a tmux error popup; every key
that delivers text calls =display-message= — directly for =w= and =l=, through
to-claude for =W= and =L=; =seek back= delivers nothing and therefore says nothing.

Word grain routes to =--ref= when the text is path-shaped and =--paste= otherwise, where
path-shaped means a path containing a slash, or =file.ext:123=, or a bare =name.ext=.
The bare-filename case is an addition: thumbs' built-in =path= regexp requires a slash
and =@thumbs-regexp-1= requires a =:digits= suffix, so =main.rs= matched neither.

This ticket also closes an open item the edge-case grill left behind: the hybrid grain
was constraining the copy-pipe route, and choosing wl-copy removes the constraint
instead of resolving it.

*** Question

The destination review found four defects in the one @seek_origin mechanism, which is
a redesign pass rather than four patches. All four are in
[[file:assets/destination-review-2026-08-09.md][the 2026-08-09 destination review]], blocker 3.

1. Consumed before it can be read. Both this map and the 1218 grill snapshot say the
   stamp is "consumed with `set -p -u` and consumed *before* seek acts". Read literally
   the unset precedes the read, leaving nothing to compare the cursor against. The
   intent was read, then unset, then act — the text never says so.
2. It cannot distinguish "no search happened" from "the search found nothing". Both
   leave cursor == stamp — measured: a non-matching query leaves the cursor unmoved —
   yet the message set specifies two different strings for those two states.
3. A cancelled search reads as live. Measured during the effort: Escape leaves the
   cursor on the match (x=8 y=20 both before and after), so pressing `w` after
   cancelling grabs the match the user just abandoned.
4. One-shot consumption makes the five keys single-use. A second output key after the
   same search finds no stamp, silently degrades to grabber grain, and for a
   multi-token query returns only the first word.

Also fold in two should-fix items the review attached to the same mechanism: whether
re-pressing an output key is supported at all, and that the false-negative rationale
assumed entry at the pane bottom — `prefix C-t` (tmux.conf:19) followed by
`prefix Space` starts mid-screen on real text, where a match on the origin cell stops
being improbable.

Decide the liveness contract as a whole. If the stamp survives, say exactly when it is
written, read and cleared, and what each of the three fail-closed states looks like.

*** Resolution

Settled in [[file:grill/2026-08-09-1443-origin-stamp-redesign.org][the 2026-08-09-1443 grill snapshot]] — ten decisions with their measurements,
seven rejected alternatives, three open items. The headline decision graduated to
[[file:../../docs/adr/0003-detect-search-liveness-via-search-present.org][ADR-0003]].

The four review defects are resolved structurally, not patched:

1. Consumed-before-read — gone with the stamp. seek writes nothing, so nothing is
   consumed.
2. No-search vs no-match indistinguishable — merged deliberately. Both are
   =search_present=0=; the keys act as uniform grabbers there and the one remaining
   fail-closed state is an empty cursor cell.
3. Cancelled search reads as live — accepted. =search_present= stays 1 after Escape
   (measured), tmux offers no Enter/Escape distinction, and the cursor is visibly on
   the abandoned match; grabbing it grabs what the screen shows.
4. Single-use keys — gone. =search_present= persists across repeated grabs, and
   delivery now exits copy-mode anyway (house =copy-pipe-and-cancel= style), which
   this map had never actually decided before.

Two discoveries feed later tickets:

- Backward search lands on the match start (forward x=7 vs backward x=4, same content,
  same query). The =cursor-left= correction and the =v= key are deleted; the end+1
  claim in the 1116 snapshot was a forward-only measurement applied to a backward
  design.
- seek no longer issues =send-keys= during operation, so the unverified =run-shell=
  timing item in [[#t8][Binding placement and load ordering]] dissolves, and the =v=-silence
  item in [[#t7][Status-line message safety and shape]] dissolves with the key.

The grain rule as it now stands: =search_present=1= and whitespace in the query →
deliver =pane_search_string= verbatim; otherwise =copy_cursor_word= / =copy_cursor_line=
under the cursor. This gives [[#t9][Undefined input semantics]] a defined default for
whitespace-bearing queries; trim-or-not stays that ticket's decision.

*** Question

As specified, nobody delivers the clipboard half on the `W` and `L` paths, and the tmux
buffer half was dropped somewhere between the design interview and ADR-0002. See
[[file:assets/destination-review-2026-08-09.md][the destination review]], blocker 2.

The trail: the 1116 design snapshot's decision 3 says seek takes over all three thumbs
outputs — "cursor jump, `wl-copy` + `set-buffer`, and `to-claude`". ADR-0001's drivers
repeat `tmux set-buffer`. ADR-0002's decision text says only "pipe it to `wl-copy`".
Ticket t3's per-key table reports `→ CLIP` for `w` / `l` and "to-claude speaks" for
`W` / `L`, and never assigns the clipboard on that second path. Verified in the source:
tmux.conf lines 57 and 68 both do `wl-copy && tmux set-buffer`, and `to-claude --ref`
does not touch the clipboard — only its `--paste` mode does. So `W` as specified
delivers to Claude and clipboards nothing, which is exactly the regression the comment
at tmux.conf lines 63-66 records having already been fixed once.

Two questions to settle together, because the answer to the first shapes the second:

1. Does seek write the tmux buffer as well as the Wayland clipboard? Dropping
   `set-buffer` regresses `prefix ]`, which cheat.txt advertises.
2. What happens when `wl-copy` is missing or fails, and when `to-claude` fails?
   ADR-0002 declares a hard dependency on wl-copy and nothing states the failure
   behaviour; combined with the exit-0 convention and no message, the clipboard half
   fails silently. Note `to-claude` exits 1 on "no marked pane and no claude pane", so
   seek must be told whether to swallow that code — a non-zero exit becomes a tmux
   error popup.

*** Resolution

Settled in [[file:grill/2026-08-09-1452-clipboard-delivery-ownership.org][the 2026-08-09-1452 grill snapshot]] — five decisions, six rejected
alternatives. No ADR: every piece is a one-or-two-line reversible contract detail, and
ADR-0002 stands unamended (it chose the wl-copy route; a second sink is not a route
change).

The two questions this ticket asked, answered:

1. Yes — seek writes the tmux buffer as well. All four keys do =wl-copy= + =set-buffer=
   before anything else, restoring what the design snapshot and ADR-0001 promised and
   what both thumbs commands actually did. =prefix ]= keeps working and the buffer is
   the fallback sink when wl-copy is gone. On =L=, to-claude's =--paste= writes the
   clipboard a second time with the same bytes (verified: =Mode::Paste= calls
   =copy_to_clipboard=, =Mode::Ref= does not) — accepted as harmless rather than
   modifying a sibling tool five call sites share.

2. The failure contract:
   - wl-copy missing or failing → degrade, never refuse: =set-buffer= still happens,
     exit stays 0, and on =w= / =l= the message changes to a =→ BUFFER <text>
     (wl-copy failed)= shape. The house silent-best-effort precedent is deliberately
     not followed there, because on the lowercase keys the clipboard is the primary
     deliverable rather than a side channel.
   - On =W= / =L= a wl-copy failure stays silent — the primary deliverable there is
     the Claude pane, and seek's clipboard write precedes the to-claude call, so any
     failure message would be overwritten by =→ CLAUDE= anyway. Rule of thumb recorded:
     the message reports the primary deliverable's fate.
   - to-claude exiting 1 is swallowed; seek always exits 0. Verified that to-claude's
     =fail()= already display-messages and stderr-prints its own failures, so
     propagating the code would only add a tmux error popup on top.

This close unblocks [[#t7][Status-line message safety and shape]], which owns the exact
message strings and their sanitization.
